## 1. Цели

1. **Ценность карты (Card Value)** — у каждой карточки появляется числовой параметр «ценность», вычисляемый по редкости и достижениям. Это «зарплата» карточки — не цена продажи и не цена переработки.

2. **Глобальный рейтинг** — рейтинг всех участников фэнтези по суммарной ценности портфеля (баланс фантиков + Σ ценностей всех карточек).

3. **Система лиг** — в каждой серии доступны несколько лиг с разными правилами (например, ограничение по суммарной ценности команды). Из основной лиги убрано ограничение на 1 легендарную карту.

4. **Основа для пользовательских лиг** — модель данных позволяет в будущем дать пользователям создавать свои лиги с кастомными правилами.

## 2. Ценность карты

### 2.1 Формула

```
card_value = base_rarity_value + (achievement_count × achievement_value_bonus)
```

| Параметр | Источник | Описание |
|----------|----------|----------|
| `base_rarity_value` | `economy_config`: `card.value.COMMON` / `.RARE` / `.EPIC` / `.LEGENDARY` | Базовая ценность по редкости |
| `achievement_count` | Число ачивок на `card_template` | Количество достижений шаблона |
| `achievement_value_bonus` | `economy_config`: `card.value.achievement_bonus` | Бонус к ценности за каждое достижение |

### 2.2 Референсные значения

Подобраны так, чтобы бюджетная лига с капом ~1500 создавала интересные trade-off (нельзя 3 эпика, но можно легендарку + два коммона):

| Редкость | Ачивок | base | + ачивки | Итого |
|----------|--------|------|----------|-------|
| COMMON   | 0      | 100  | 0        | **100** |
| RARE     | 1      | 250  | 50       | **300** |
| EPIC     | 2      | 500  | 100      | **600** |
| LEGENDARY| 3      | 1000 | 150      | **1150** |

При кэпе 1500:
- 3× LEGENDARY — 3450 — **нельзя**
- 1× LEGENDARY + 1× EPIC + 1× COMMON — 1150 + 600 + 100 = 1850 — **нельзя**
- 1× LEGENDARY + 2× COMMON — 1150 + 100 + 100 = 1350 — **можно** ✓
- 1× EPIC + 2× RARE — 600 + 300 + 300 = 1200 — **можно** ✓
- 3× EPIC — 600 × 3 = 1800 — **нельзя**
- 2× EPIC + 1× COMMON — 600 + 600 + 100 = 1300 — **можно** ✓
- 1× LEGENDARY + 1× RARE + 1× COMMON — 1150 + 300 + 100 = 1550 — **нельзя** (пограничный)
- 5× COMMON (если бы max_team_size = 5) — 500 — **можно** ✓

Значения задаются через `economy_config` и редактируются в админке — можно подстраивать баланс без выкатки кода.

### 2.3 Три «цены» карты — разграничение

| Понятие | Назначение | Определяется | Типичное соотношение |
|---------|-----------|-------------|---------------------|
| **Ценность (value)** | Зарплатный кэп лиг, глобальный рейтинг | Формула (rarity + achievements) | Базовая единица |
| **Цена переработки (recycle)** | Сколько фантиков за уничтожение карты | `economy_config` `recycle.value.*` | ~30–50% от ценности |
| **Рыночная цена (marketplace)** | Цена на маркетплейсе (задаёт продавец) | Игрок, в рамках min/max по редкости | Рыночная, может быть выше/ниже ценности |

Ценность **не конвертируется в фантики напрямую** — это отдельная метрика. Но для глобального рейтинга ценность карт суммируется с балансом фантиков, создавая единый показатель «богатства».

### 2.4 Когда ценность пересчитывается

Ценность вычисляется **на лету** по формуле — не хранится в БД. Это гарантирует:
- Изменение `economy_config` мгновенно влияет на все карты
- EPIC → LEGENDARY апгрейд автоматически увеличивает ценность (новая редкость + ачивка)
- Нет рассинхрона между формулой и хранимым значением

Для тяжёлых запросов (глобальный рейтинг) — кэширование на уровне сервиса.

## 3. Глобальный рейтинг

### 3.1 Формула

```
portfolio_value = fantiki_balance + Σ(card_value(card)) для всех card ∈ user_cards
```

Учитываются **все** карточки пользователя, включая:
- Карты с `uses_remaining = 0` (истёкшие) — полная ценность
- Карты на маркетплейсе (ACTIVE listing) — полная ценность (они всё ещё принадлежат продавцу)

### 3.2 Мета-игра

Глобальный рейтинг создаёт мета-слой поверх основной игры:

| Действие | Влияние на рейтинг |
|----------|-------------------|
| Открытие пака за 200₣ | −200₣ баланс, +Σ(card_values) карт. Если суммарная ценность > 200 → рейтинг растёт |
| Победа в серии (награда) | +фантики → рейтинг растёт |
| Переработка карты | +recycle_value₣, −card_value. Обычно recycle < value → рейтинг падает |
| Покупка на маркетплейсе за 150₣, ценность карты 300 | −150₣ + 300 ценности → рейтинг +150 |
| Продажа на маркетплейсе за 400₣, ценность карты 300 | +400₣ (минус комиссия) − 300 → рейтинг немного растёт |
| EPIC → LEGENDARY апгрейд | −upgrade_cost₣, +(legendary_value − epic_value + achievement_bonus) |

Это мотивирует:
- Не переработать ценные карты бездумно
- Покупать карты дешевле их ценности (арбитраж)
- Копить коллекцию


Ответ:

### 3.4 Производительность

Запрос глобального рейтинга требует агрегации по всем пользователям и их картам. Оптимизация:

1. **SQL-уровень**: одним запросом с `JOIN` и `GROUP BY`:
   ```sql
   SELECT tu.id, tu.fantiki,
          COALESCE(SUM(base_value + achievement_count * bonus), 0) AS cards_value,
          tu.fantiki + COALESCE(SUM(...), 0) AS total_value
   FROM telegram_user tu
   LEFT JOIN user_card uc ON uc.telegram_user_id = tu.id
   LEFT JOIN card_template ct ON ct.id = uc.card_template_id
   LEFT JOIN (SELECT card_template_id, COUNT(*) as cnt
              FROM card_template_achievement GROUP BY card_template_id) cta
          ON cta.card_template_id = ct.id
   GROUP BY tu.id
   ORDER BY total_value DESC
   ```

2. **Кэш**: `@Cacheable` с TTL 5 минут (инвалидация при финализации серии, крупных транзакциях).

3. **Отложенная оптимизация**: если пользователей > 1000 — materialized view или периодический snapshot.

## 4. Система лиг

### 4.1 Концепция

**Лига** — набор правил для формирования фэнтези-команды на серию. Каждая серия может иметь несколько лиг. У каждой лиги — свой лидерборд и своя награда.

Системные лиги (V1):

| Лига | Правила | Назначение |
|------|---------|-----------|
| **Основная** (Main) | Без ограничений (ни по ценности, ни по числу легендарок) | Чистая оптимизация: лучшие карты = лучший результат |
| **Бюджетная** (Budget) | `sum(card_value) ≤ value_cap` (из `economy_config`) | Стратегическая глубина: нужно оптимизировать соотношение ценность/перформанс |

### 4.2 Правила лиги

| Правило | Тип | Описание |
|---------|-----|----------|
| `value_cap` | BIGINT nullable | Максимальная суммарная ценность команды. NULL = без ограничения |
| `max_legendary_count` | INT nullable | Макс. легендарок в команде. NULL = без ограничения |
| `min_team_size` | INT | Минимум карт в команде (default 1) |
| `max_team_size` | INT | Максимум карт в команде (default 3) |

**Важно:** текущее ограничение `legendary.team.max_per_series = 1` в `economy_config` **заменяется** лиговым правилом `max_legendary_count`. В основной лиге = NULL (без ограничения), в бюджетной — тоже NULL (ценность кэп сам по себе ограничивает дорогие карты).

### 4.3 Одна карта — две лиги

Одна и та же `user_card` может быть выставлена в команды разных лиг в рамках одной серии. При финализации серии `uses_remaining` каждой **уникальной** карточки, использованной хотя бы в одной лиге, уменьшается на 1.

Пример:
- Карта A в Основной лиге, карты B и C в Бюджетной лиге → финализация: A, B, C теряют по 1 use
- Карта A в обеих лигах, карта B только в Основной → финализация: A и B теряют по 1 use (А не теряет 2)

### 4.4 Награды

Каждая лига имеет свой **масштаб наград** (`reward_scale`), умножаемый на стандартную таблицу наград серии.

| Лига | `reward_scale` | 1-е место (при базе 500₣) |
|------|---------------|--------------------------|
| Основная | 1.0 | 500₣ |
| Бюджетная | 0.5 | 250₣ |

Масштаб задаётся через `economy_config` (`league.reward_scale.MAIN`, `league.reward_scale.BUDGET`). Таблица наград по местам — та же (`series.reward.*`), умноженная на `reward_scale`.

При финализации серии:
1. Для каждой лиги серии — отдельный лидерборд и отдельное начисление наград
2. `uses_remaining` уменьшается **один раз** за серию, не за лигу
3. Масштабирование за неполный состав (`scaleSeriesRewardByRosterSize`) применяется к каждой лиге отдельно

### 4.5 Стратегическая глубина бюджетной лиги

Бюджетная лига меняет мета-игру:

| В основной лиге | В бюджетной лиге |
|----------------|-----------------|
| LEGENDARY всегда лучше EPIC | LEGENDARY «стоит» 1150, EPIC «стоит» 600. Легендарка съедает большую часть бюджета |
| Коллекция ценных карт — преимущество | Нужны «хорошие дешёвые» карты — COMMON/RARE с сильными ачивками |
| Апгрейд EPIC→LEGENDARY — всегда хорошо | Апгрейд делает карту непригодной для бюджетной лиги |
| Маркетплейс: покупай дорогое | Маркетплейс: ищи перформанс/ценность |

Это создаёт дифференцированный спрос на карты всех редкостей.

## 5. Взаимодействие с существующими механиками

### 5.1 Маркетплейс

- **Ценность на карточке листинга**: пользователь видит «ценность 300, цена продавца 200» — понимает, что это выгодная сделка для рейтинга.
- **Бюджетная лига повышает спрос на COMMON/RARE**: дешёвые карты с сильными ачивками становятся стратегически ценными → маркетплейс оживляется для всех редкостей.
- **Нижняя граница цены**: `marketplace.min_price.*` может быть привязана к ценности (например, min_price ≥ 50% card_value), но это отдельное решение.

### 5.2 Legendary Upgrade

- Апгрейд увеличивает ценность карты (~600 → ~1150).
- Если карта стоит в бюджетной команде и после апгрейда сумма превышает кэп → **карта снимается с бюджетной команды** (до дедлайна) или **апгрейд блокируется**, если дедлайн прошёл и команда зафиксирована.
- **Рекомендация**: блокировать апгрейд, если карта в активной (не финализированной) бюджетной команде. Пользователь должен сначала убрать карту из бюджетной лиги.

### 5.3 Открытие паков

- При открытии пака можно показать «суммарная ценность выпавших карт: 950» vs «цена пака: 200₣» → ощущение ценности покупки.
- Для бюджетной лиги: выпавшие дешёвые карты с хорошими ачивками — это не «плохой дроп», а стратегический ресурс.

### 5.4 Переработка и продление

- Переработка уничтожает ценность из портфеля: recycle_value < card_value → рейтинг падает.
- Продление (renewal) не меняет ценность — карта та же, только uses_remaining восстановлен.
- Это мотивирует не перерабатывать карты бездумно, а продавать на маркетплейсе.

### 5.5 Ростер серии (pruning)

- `FantasyTeamRosterPruningService` уже удаляет карты из команды, если игрок покинул ростер.
- С лигами: pruning применяется к командам **всех лиг** серии.
- Логика не меняется — тот же алгоритм, но для каждой `(fantasy_team, league)` пары.

### 5.6 Планировщик (sync + scoring)

- `ActiveSeriesSyncScheduler` считает очки для серии — без изменений.
- Скоринг не зависит от лиги: одни и те же игры, одна формула.
- Лидерборд per-league строится из тех же `FantasyTeam.total_score`, просто фильтруется по `series_league_id`.

### 5.7 Финализация серии

Расширение `SeriesFinalizationService.finalizeSeries`:

```
1. Для каждой лиги серии (SeriesLeague):
   a. Построить лидерборд по total_score (как сейчас, но отфильтровать по league)
   b. Начислить награды с учётом reward_scale и scaleSeriesRewardByRosterSize

2. Собрать DISTINCT множество user_card_id по всем командам всех лиг серии
3. Для каждого уникального user_card: uses_remaining -= 1

4. series.finalized = true
```

## 6. Модель данных

### 6.1 Новые ключи `economy_config`

| Key | Default | Description |
|-----|---------|-------------|
| `card.value.COMMON` | `100` | Базовая ценность COMMON |
| `card.value.RARE` | `250` | Базовая ценность RARE |
| `card.value.EPIC` | `500` | Базовая ценность EPIC |
| `card.value.LEGENDARY` | `1000` | Базовая ценность LEGENDARY |
| `card.value.achievement_bonus` | `50` | Бонус за каждое достижение на карте |
| `league.reward_scale.MAIN` | `100` | Масштаб наград основной лиги (%) |
| `league.reward_scale.BUDGET` | `50` | Масштаб наград бюджетной лиги (%) |
| `league.budget.value_cap` | `1500` | Кэп ценности для бюджетной лиги |

### 6.2 Таблица `league`

```sql
CREATE TABLE league (
    id          BIGSERIAL PRIMARY KEY,
    code        VARCHAR(32) NOT NULL UNIQUE,  -- 'MAIN', 'BUDGET', пользовательские = UUID
    name        VARCHAR(128) NOT NULL,
    description TEXT,
    league_type VARCHAR(32) NOT NULL,          -- 'SYSTEM' | 'USER'
    
    -- правила (для SYSTEM лиг часть правил в economy_config)
    value_cap           BIGINT,                -- NULL = без ограничения
    max_legendary_count INT,                   -- NULL = без ограничения
    min_team_size       INT NOT NULL DEFAULT 1,
    max_team_size       INT NOT NULL DEFAULT 3,
    
    -- для USER лиг (V2+)
    created_by_telegram_user_id BIGINT REFERENCES telegram_user(id),
    visibility  VARCHAR(32) DEFAULT 'PUBLIC',  -- PUBLIC | PRIVATE | INVITE_ONLY
    entry_fee   BIGINT DEFAULT 0,
    
    created_at  TIMESTAMP NOT NULL DEFAULT NOW()
);
```

Seed-данные:

```sql
INSERT INTO league (code, name, description, league_type)
VALUES
    ('MAIN', 'Основная лига', 'Без ограничений по ценности и редкости', 'SYSTEM'),
    ('BUDGET', 'Бюджетная лига', 'Суммарная ценность команды ограничена', 'SYSTEM');
```

### 6.3 Таблица `series_league`

Связь «какие лиги доступны в серии» + настройки на уровне серии:

```sql
CREATE TABLE series_league (
    id          BIGSERIAL PRIMARY KEY,
    series_id   BIGINT NOT NULL REFERENCES series(id),
    league_id   BIGINT NOT NULL REFERENCES league(id),
    
    -- override правил для этой серии (если NULL — берём из league / economy_config)
    value_cap_override    BIGINT,
    reward_scale_override INT,    -- процент (100 = полная награда)
    
    enabled     BOOLEAN NOT NULL DEFAULT TRUE,
    
    UNIQUE (series_id, league_id)
);
```

При создании серии: автоматически создаются записи `series_league` для всех SYSTEM-лиг.

### 6.4 Изменение `fantasy_team`

```sql
ALTER TABLE fantasy_team
    ADD COLUMN series_league_id BIGINT REFERENCES series_league(id);

-- Миграция: все существующие команды → основная лига
UPDATE fantasy_team ft
SET series_league_id = sl.id
FROM series_league sl
JOIN league l ON l.id = sl.league_id
WHERE sl.series_id = ft.series_id AND l.code = 'MAIN';

ALTER TABLE fantasy_team ALTER COLUMN series_league_id SET NOT NULL;

-- Обновить UNIQUE constraint
ALTER TABLE fantasy_team DROP CONSTRAINT fantasy_team_telegram_user_id_series_id_key;
ALTER TABLE fantasy_team ADD CONSTRAINT fantasy_team_user_series_league_key
    UNIQUE (telegram_user_id, series_id, series_league_id);
```

### 6.5 Для пользовательских лиг (V2+, закладка)

```sql
-- Членство в пользовательских лигах
CREATE TABLE league_member (
    id          BIGSERIAL PRIMARY KEY,
    league_id   BIGINT NOT NULL REFERENCES league(id),
    telegram_user_id BIGINT NOT NULL REFERENCES telegram_user(id),
    joined_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    UNIQUE (league_id, telegram_user_id)
);
```

Не создаём в V1, но модель `league` уже содержит поля `created_by_telegram_user_id`, `visibility`, `entry_fee`.

## 7. API

### 7.1 User API — ценность и рейтинг

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/card-value/info` | Параметры формулы ценности (base per rarity, achievement bonus) |
| GET | `/api/v1/rating` | Глобальный рейтинг по ценности портфеля |

### 7.2 User API — лиги

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/series/{id}/leagues` | Доступные лиги серии (правила, текущая команда пользователя) |
| GET | `/api/v1/series/{id}/leagues/{leagueCode}/leaderboard` | Лидерборд лиги серии |
| POST | `/api/v1/series/{id}/leagues/{leagueCode}/fantasy-team` | Отправить команду на лигу |
| PUT | `/api/v1/series/{id}/leagues/{leagueCode}/fantasy-team` | Обновить команду лиги |
| GET | `/api/v1/series/{id}/leagues/{leagueCode}/users/{telegramId}/fantasy-team` | Чужая команда в лиге |
| GET | `/api/v1/series/{id}/leagues/{leagueCode}/users/{telegramId}/fantasy-team/details` | Детализация чужой команды |

### 7.3 Обратная совместимость

Существующие endpoint'ы серии **сохраняются** и работают как обёртка над основной лигой:

| Старый endpoint | Поведение |
|----------------|-----------|
| `GET /series/{id}/leaderboard` | → лидерборд основной лиги (code=`MAIN`) |
| `POST /series/{id}/fantasy-team` | → команда в основной лиге |
| `PUT /series/{id}/fantasy-team` | → обновление команды основной лиги |

### 7.4 Admin API

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/admin/leagues` | Все лиги (системные + будущие пользовательские) |

## 8. UI/UX

### 8.1 Ценность на карточке

- На каждой карточке (коллекция, маркетплейс, команда) — бейдж с ценностью: например, `₱300` (значок ценности, не фантика).
- В модалке карточки — расшифровка: «Ценность: 250 (редкость) + 50 (1 достижение) = 300».
- В маркетплейсе рядом с ценой продавца — ценность карты для сравнения.

### 8.2 Глобальный рейтинг

- Новый пункт навигации: «Рейтинг».
- Таблица: ранг, ник, баланс фантиков, ценность карт, итого.
- Текущий пользователь выделен и всегда виден (даже если далеко в списке).

### 8.3 Лиги в серии

- На странице серии — вкладки лиг: «Основная» / «Бюджетная».
- Каждая вкладка: свой лидерборд, своя команда.
- При сборке команды в бюджетной лиге:
  - Прогресс-бар «Бюджет: 1200 / 1500₱».
  - Карты, которые не влезают в оставшийся бюджет — визуально заглушены (disabled).
  - Подсказка «Эта карта стоит 600₱, осталось 300₱ бюджета».

### 8.4 Справка (`/help`)

Дополнить раздел:
- **Ценность карты**: формула, таблица значений.
- **Глобальный рейтинг**: как считается, что влияет.
- **Лиги**: правила основной и бюджетной лиг, отдельные награды.

### 8.5 Выбор серии / главная

- На карточке серии показать, какие лиги доступны (иконки/бейджи).
- На главной «Состав на серию» — если есть команда только в одной лиге, подсказка «Собери команду в бюджетной лиге!».

## 9. Пользовательские лиги (V2+, концепция)

Основа заложена в модели данных (§6.2). Пользовательские лиги расширят систему:

### 9.1 Создание лиги

Пользователь в TMA:
1. Нажимает «Создать лигу».
2. Задаёт имя, описание, правила (value_cap, max_legendary, team_size).
3. Опционально: входной взнос (фантики), видимость (публичная / по инвайту).
4. Получает код/ссылку для приглашения.

### 9.2 Членство

- Пользователи вступают в лигу (принимают инвайт или находят публичную).
- Для серий, в которых лига активна, участники собирают команды по правилам лиги.
- Лидерборд лиги — только среди участников.

### 9.3 Модерация

- Создатель лиги может кикнуть участника.
- Админ может заблокировать/удалить пользовательскую лигу.

### 9.4 Экономика

- Входной взнос → призовой фонд лиги → распределяется по лидерборду при финализации.
- Комиссия платформы с призового фонда (как на маркетплейсе).

### 9.5 Активация для серии

- Системные лиги активируются автоматически.
- Пользовательские лиги: создатель выбирает, в каких сериях лига участвует (из доступных серий турниров).

## 10. Миграция и обратная совместимость

### 10.1 Flyway-миграция

1. Добавить ключи `economy_config` для ценности и лиг.
2. Создать таблицу `league`, seed системных лиг (MAIN, BUDGET).
3. Создать таблицу `series_league`, заполнить для всех существующих серий.
4. Добавить `fantasy_team.series_league_id`, мигрировать данные → MAIN лига.
5. Обновить UNIQUE constraint.
6. Удалить ключ `legendary.team.max_per_series` из `economy_config` (правило переехало в лигу; или оставить deprecated).

### 10.2 Обратная совместимость API

- Старые endpoint'ы fantasy-team и leaderboard работают как proxy к MAIN лиге.
- TMA до обновления фронтенда работает без изменений (видит только основную лигу).
- Бюджетная лига появляется для пользователя только после обновления TMA.
