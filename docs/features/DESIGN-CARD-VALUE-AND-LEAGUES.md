## 1. Цели

1. **Ценность карты (Card Value)** — у каждой карточки появляется числовой параметр «ценность», вычисляемый по редкости и достижениям. Это «зарплата» карточки — не цена продажи и не цена переработки.

2. **Глобальный рейтинг** — рейтинг всех участников фэнтези по суммарной ценности портфеля (баланс фантиков + Σ ценностей всех карточек).

3. **Система лиг** — в каждой серии доступны несколько лиг с разными правилами (например, ограничение по суммарной ценности команды). Из основной лиги убрано ограничение на 1 легендарную карту.

4. **Основа для пользовательских лиг** — модель данных позволяет в будущем дать пользователям создавать свои лиги с кастомными правилами.

## 2. Ценность карты

### 2.1 Формула

```
card_value = base_rarity_value + (achievement_count × achievement_value_bonus)
```

| Параметр | Источник | Описание |
|----------|----------|----------|
| `base_rarity_value` | `economy_config`: `card.value.COMMON` / `.RARE` / `.EPIC` / `.LEGENDARY` | Базовая ценность по редкости |
| `achievement_count` | Число ачивок на `card_template` | Количество достижений шаблона |
| `achievement_value_bonus` | `economy_config`: `card.value.achievement_bonus` | Бонус к ценности за каждое достижение |

### 2.2 Референсные значения

**Принято (продукт):** `card.value.achievement_bonus` = **10**; базы `card.value.*`: **COMMON 25**, RARE **40**, EPIC **80**, LEGENDARY **370**. Бюджетная лига: **`league.budget.value_cap` = 175** (см. §6.1, §14).

| Редкость | Ачивок (реф.) | base | + ачивки | Итого |
|----------|---------------|------|----------|-------|
| COMMON   | 0             | 25   | 0        | **25** |
| RARE     | 1             | 40   | 10       | **50** |
| EPIC     | 2             | 80   | 20       | **100** |
| LEGENDARY| 3             | 370  | 30       | **400** |

**Бюджет (TMA):** `value_cap` = **175**; при 3 карт-росте «радуга» 1C+1R+1E даёт **25+50+100=175** — ровно в кэп. Любой состав **с L** в 3 слотах: мин. **2C+L = 450** → **> 175**; леги в бюджете — **нет**, только **MAIN** для полного пула редкостей.

Значения задаются через `economy_config` и редактируются в админке — можно подстраивать баланс без выкатки кода.

### 2.3 Три «цены» карты — разграничение

| Понятие | Назначение | Определяется | Типичное соотношение |
|---------|-----------|-------------|---------------------|
| **Ценность (value)** | Зарплатный кэп лиг, глобальный рейтинг | Формула (rarity + achievements) | Базовая единица |
| **Цена переработки (recycle)** | Сколько фантиков за уничтожение карты | `economy_config` `recycle.value.*` | ~40–60% от ценности |
| **Рыночная цена (marketplace)** | Цена на маркетплейсе (задаёт продавец) | Игрок, в рамках min/max по редкости | Рыночная, может быть выше/ниже ценности |

Ценность **не конвертируется в фантики напрямую** — это отдельная метрика. Но для глобального рейтинга ценность карт суммируется с балансом фантиков, создавая единый показатель «богатства».

### 2.4 Когда ценность пересчитывается

Ценность вычисляется **на лету** по формуле — не хранится в БД. Это гарантирует:
- Изменение `economy_config` мгновенно влияет на все карты
- EPIC → LEGENDARY апгрейд автоматически увеличивает ценность (новая редкость + ачивка)
- Нет рассинхрона между формулой и хранимым значением

Для тяжёлых запросов (глобальный рейтинг) — кэширование на уровне сервиса.

## 3. Глобальный рейтинг

### 3.1 Формула

```
portfolio_value = fantiki_balance + Σ(card_value(card)) для всех card ∈ user_cards
```

Учитываются **все** карточки пользователя, включая:
- Карты с `uses_remaining = 0` (истёкшие) — полная ценность
- Карты на маркетплейсе (ACTIVE listing) — полная ценность (они всё ещё принадлежат продавцу)

### 3.2 Мета-игра

Глобальный рейтинг создаёт мета-слой поверх основной игры:

| Действие | Влияние на рейтинг |
|----------|-------------------|
| Открытие пака за 200₣ | −200₣ баланс, +Σ(card_values) карт. Если суммарная ценность > 200 → рейтинг растёт |
| Победа в серии (награда) | +фантики → рейтинг растёт |
| Переработка карты | +recycle_value₣, −card_value. Обычно recycle < value → рейтинг падает |
| Покупка на маркетплейсе за 150₣, ценность карты 100 (EPIC) | −150₣ + 100 ценности → рейтинг −50, если 100<150 |
| Продажа на маркетплейсе за 400₣, ценность карты 400 (LEG) | +400₣ (минус комиссия) − 400 → рейтинг зависит от комиссии |
| EPIC → LEGENDARY апгрейд | −upgrade_cost₣, +(legendary_value − epic_value + achievement_bonus) |

Это мотивирует:
- Не переработать ценные карты бездумно
- Покупать карты дешевле их ценности (арбитраж)
- Копить коллекцию

### 3.3 API

```
GET /api/v1/rating
```

Ответ:

```json
{
  "entries": [
    {
      "rank": 1,
      "user": { "telegramId": 123, "displayName": "PlayerOne" },
      "fantikiBalance": 5000,

      "cardsCount": 28
    }
  ],
  "currentUser": {
    "rank": 42,
    "fantikiBalance": 1200,
    "cardsValue": 3400,
    "totalValue": 4600,
    "cardsCount": 8
  }
}
```

### 3.4 Производительность

Запрос глобального рейтинга требует агрегации по всем пользователям и их картам. Оптимизация:

1. **SQL-уровень**: одним запросом с `JOIN` и `GROUP BY`:
   ```sql
   SELECT tu.id, tu.fantiki,
          COALESCE(SUM(base_value + achievement_count * bonus), 0) AS cards_value,
          tu.fantiki + COALESCE(SUM(...), 0) AS total_value
   FROM telegram_user tu
   LEFT JOIN user_card uc ON uc.telegram_user_id = tu.id
   LEFT JOIN card_template ct ON ct.id = uc.card_template_id
   LEFT JOIN (SELECT card_template_id, COUNT(*) as cnt
              FROM card_template_achievement GROUP BY card_template_id) cta
          ON cta.card_template_id = ct.id
   GROUP BY tu.id
   ORDER BY total_value DESC
   ```

2. **Кэш**: `@Cacheable` с TTL 5 минут (инвалидация при финализации серии, крупных транзакциях).

3. **Отложенная оптимизация**: если пользователей > 1000 — materialized view или периодический snapshot.

## 4. Система лиг

### 4.1 Концепция

**Лига** — набор правил для формирования фэнтези-команды на серию. Каждая серия может иметь несколько лиг. У каждой лиги — свой лидерборд и своя награда.

Системные лиги (V1):

| Лига | Правила | Назначение |
|------|---------|-----------|
| **Основная** (Main) | Без ограничений (ни по ценности, ни по числу легендарок) | Чистая оптимизация: лучшие карты = лучший результат |
| **Бюджетная** (Budget) | `sum(card_value) ≤ value_cap` (из `economy_config`) | Стратегическая глубина: нужно оптимизировать соотношение ценность/перформанс |

### 4.2 Правила лиги

| Правило | Тип | Описание |
|---------|-----|----------|
| `value_cap` | BIGINT nullable | Максимальная суммарная ценность команды. NULL = без ограничения |
| `max_legendary_count` | INT nullable | Макс. легендарок в команде. NULL = без ограничения |
| `min_team_size` | INT | Минимум карт в команде (default 1) |
| `max_team_size` | INT | Максимум карт в команде (default 3) |

**Важно:** текущее ограничение `legendary.team.max_per_series = 1` в `economy_config` **заменяется** лиговым правилом `max_legendary_count`. В основной лиге = NULL (без ограничения), в бюджетной — тоже NULL (ценность кэп сам по себе ограничивает дорогие карты).

### 4.3 Одна карта — несколько лиг

Одна и та же `user_card` может быть выставлена в команды разных лиг в рамках одной серии. **Каждая лига стоит одно использование** — при финализации `uses_remaining` уменьшается на количество лиг, в которых карта участвовала.

**Ограничение при сборке команды:** карта может быть в команде одновременно **не более чем `uses_remaining` лиг** данной серии. Если у карты 1 use — только в одной лиге, 3 uses — до трёх лиг.

Валидация при `POST/PUT .../fantasy-team`:
1. Подсчитать, в скольких лигах **этой серии** карта уже стоит (исключая текущую лигу, если это update)
2. `existing_league_count + 1 > uses_remaining` → отклонить (`400`)

Пример (карта с `uses_remaining = 2`):
- Поставлена в Основную → OK (1 ≤ 2). Поставлена ещё и в Бюджетную → OK (2 ≤ 2)
- Финализация: `uses_remaining -= 2` → осталось 0
- Если бы `uses_remaining = 1`: в Основную → OK, в Бюджетную → **отклонено** (2 > 1), выбирай одну

Это создаёт дополнительную ценность карт с бОльшим запасом uses:
- Высокая редкость по умолчанию даёт больше uses → больше лиг
- Renewal восстанавливает uses → открывает доступ к дополнительным лигам
- Стратегический выбор: в какую лигу отправить карту с 1 use?

### 4.4 Награды

Каждая лига имеет свой **масштаб наград** (`reward_scale`), умножаемый на стандартную таблицу наград серии.

| Лига | `reward_scale` | 1-е место (при базе 500₣) |
|------|---------------|--------------------------|
| Основная | 1.0 | 500₣ |
| Бюджетная | 0.5 | 250₣ |

Масштаб задаётся через `economy_config` (`league.reward_scale.MAIN`, `league.reward_scale.BUDGET`). Таблица наград по местам — та же (`series.reward.*`), умноженная на `reward_scale`.

При финализации серии:
1. Для каждой лиги серии — отдельный лидерборд и отдельное начисление наград
2. `uses_remaining` каждой карты уменьшается **на количество лиг**, в которых она участвовала (1 use за лигу)
3. Масштабирование за неполный состав (`scaleSeriesRewardByRosterSize`) применяется к каждой лиге отдельно

### 4.5 Стратегическая глубина

Лиги добавляют несколько слоёв стратегии:

**Бюджетная лига меняет мета-игру:**

| В основной лиге | В бюджетной лиге |
|----------------|-----------------|
| LEGENDARY всегда лучше EPIC | Стоимость **400** vs **100** (станд. §2.2). В бюджетной с cap **175** **леги** в 3 роли **не** влезают (мин. 2C+L = **450**) |
| Коллекция ценных карт — преимущество | Нужны «хорошие дешёвые» карты — COMMON/RARE с сильными ачивками |
| Апгрейд EPIC→LEGENDARY — всегда хорошо | Апгрейд делает карту непригодной для бюджетной лиги |
| Маркетплейс: покупай дорогое | Маркетплейс: ищи перформанс/ценность |

**Управление uses добавляет дилемму:**

| uses_remaining | Доступные лиги | Trade-off |
|---------------|---------------|-----------|
| 1 | Только 1 лига | Самый сложный выбор: основная (сильная команда) или бюджетная (меньше конкуренция)? |
| 2 | До 2 лиг | Можно играть в обеих, но карта истечёт после финализации |
| 3+ | Все системные лиги + пользовательские | Свобода, но каждая лига «сжигает» use |

Это создаёт дифференцированный спрос на карты всех редкостей и мотивирует renewal.

## 5. Взаимодействие с существующими механиками

### 5.1 Маркетплейс

- **Ценность на карточке листинга**: пользователь видит «ценность 50, цена продавца 200» (пример RARE) — понимает арбитраж.
- **Бюджетная лига повышает спрос на COMMON/RARE**: дешёвые карты с сильными ачивками становятся стратегически ценными → маркетплейс оживляется для всех редкостей.
- **Нижняя граница цены**: `marketplace.min_price.*` может быть привязана к ценности (например, min_price ≥ 50% card_value), но это отдельное решение.

### 5.2 Legendary Upgrade

- Апгрейд увеличивает ценность карты (~100 → ~400 в текущем масштабе §2.2).
- **Решение**: апгрейд **блокируется**, если карта стоит в команде **любой** лиги серии с `finalized = false`. Пользователь должен сначала убрать карту из всех таких команд. Это расширяет текущую проверку `LegendaryUpgradeService` (которая уже блокирует апгрейд карт в активных листингах маркетплейса) аналогичной проверкой для лиг.

### 5.3 Открытие паков

- При открытии пака можно показать «суммарная ценность выпавших карт: 500» vs «цена пака: 200₣» (примеры) — ощущение ценности покупки.
- Для бюджетной лиги: выпавшие дешёвые карты с хорошими ачивками — это не «плохой дроп», а стратегический ресурс.

### 5.4 Переработка и продление

- Переработка уничтожает ценность из портфеля: recycle_value < card_value → рейтинг падает.
- Продление (renewal) не меняет ценность карты, но **восстанавливает uses** → карта снова может участвовать в нескольких лигах. Renewal становится ценнее: это не просто «ещё одна серия», а «ещё одна серия × N лиг».
- Это мотивирует не перерабатывать карты бездумно, а продавать на маркетплейсе.

### 5.5 Ростер серии (pruning)

- `FantasyTeamRosterPruningService` уже удаляет карты из команды, если игрок покинул ростер.
- С лигами: pruning применяется к командам **всех лиг** серии.
- Логика не меняется — тот же алгоритм, но для каждой `(fantasy_team, league)` пары.

### 5.6 Планировщик (sync + scoring)

- `ActiveSeriesSyncScheduler` считает очки для серии — без изменений.
- Скоринг не зависит от лиги: одни и те же игры, одна формула.
- Лидерборд per-league строится из тех же `FantasyTeam.total_score`, просто фильтруется по `series_league_id`.

### 5.7 Финализация серии

Расширение `SeriesFinalizationService.finalizeSeries`:

```
1. Для каждой лиги серии (SeriesLeague):
   a. Построить лидерборд по total_score (как сейчас, но отфильтровать по league)
   b. Начислить награды с учётом reward_scale и scaleSeriesRewardByRosterSize
   c. Запомнить per-league результаты для уведомлений

2. Для каждого user_card, участвовавшего хотя бы в одной лиге:
   league_count = COUNT(DISTINCT series_league_id) по командам этой серии
   uses_remaining -= league_count   (минимум 0)

3. series.finalized = true

4. Опубликовать SeriesFinalizedNotificationEvent с per-league данными
```

SQL-набросок для шага 2:
```sql
UPDATE user_card uc
SET uses_remaining = GREATEST(0, uses_remaining - sub.league_count)
FROM (
    SELECT ftc.user_card_id, COUNT(DISTINCT ft.series_league_id) AS league_count
    FROM fantasy_team_card ftc
    JOIN fantasy_team ft ON ft.id = ftc.fantasy_team_id
    WHERE ft.series_id = :seriesId
    GROUP BY ftc.user_card_id
) sub
WHERE uc.id = sub.user_card_id;
```

### 5.8 Уведомления о финализации

Текущее уведомление (одно сообщение на пользователя):

```
В турнире X подсчитаны результаты серии Y.
Победитель серии: Z.
Вы заняли 3-е место из 15 и получили в награду 500 фантиков.
Теперь у вас 2000 фантиков.
```

С лигами — **одно консолидированное сообщение** с разбивкой по лигам:

```
В турнире МФЛ подсчитаны результаты серии Тур 3.

Основная лига (15 участников):
Победитель: Alice
Вы заняли 3-е место и получили 500 фантиков.

Бюджетная лига (10 участников):
Победитель: Bob
Вы заняли 1-е место и получили 250 фантиков.

Итого за серию: +750 фантиков.
Теперь у вас 2750 фантиков.
```

**Вариации:**

- Если пользователь участвовал **только в одной лиге** — формат без явного заголовка лиги (как текущий, но с припиской «(Основная лига)»):
  ```
  В турнире X подсчитаны результаты серии Y.
  Победитель серии: Z (Основная лига).
  Вы заняли 3-е место из 15 и получили в награду 500 фантиков.
  Теперь у вас 2000 фантиков.
  ```

- Если пользователь в лиге с **нулевой наградой** (далёкое место) — всё равно показать место:
  ```
  Бюджетная лига (30 участников):
  Победитель: Charlie
  Вы заняли 28-е место.
  ```

- Если пользователь **не участвовал** в лиге — блок этой лиги не показывается.

**Изменения в модели событий:**

Текущий `SeriesFinalizedRecipient`:
```kotlin
data class SeriesFinalizedRecipient(
    val telegramId: Long,
    val place: Int,
    val total: Int,
    val reward: Long,
    val balanceAfter: Long,
)
```

Новая модель:
```kotlin
data class LeagueResult(
    val leagueName: String,
    val winnerPublicName: String?,
    val place: Int,
    val total: Int,
    val reward: Long,
)

data class SeriesFinalizedRecipient(
    val telegramId: Long,
    val leagueResults: List<LeagueResult>,
    val totalReward: Long,
    val balanceAfter: Long,
)
```

`SeriesFinalizedNotificationEvent` упрощается — победитель и место теперь per-league внутри каждого recipient:
```kotlin
data class SeriesFinalizedNotificationEvent(
    val tournamentName: String,
    val seriesName: String,
    val recipients: List<SeriesFinalizedRecipient>,
)
```

**Сборка уведомлений** в `SeriesFinalizationService`:
1. Для каждой лиги: построить лидерборд → запомнить `Map<telegramId, LeagueResult>`.
2. Объединить по `telegramId`: собрать `leagueResults` из всех лиг, где участвовал.
3. `totalReward` = сумма `reward` по всем лигам.
4. `balanceAfter` = баланс после начисления всех наград.

Функция `buildSeriesFinalizedTelegramMessage` перестраивается:
```kotlin
fun buildSeriesFinalizedTelegramMessage(
    tournamentName: String,
    seriesName: String,
    recipient: SeriesFinalizedRecipient,
): String {
    val lines = buildList {
        add("В турнире $tournamentName подсчитаны результаты серии $seriesName.")

        if (recipient.leagueResults.size == 1) {
            val lr = recipient.leagueResults.first()
            lr.winnerPublicName?.trim()?.takeIf { it.isNotEmpty() }?.let { w ->
                add("")
                add("Победитель серии: $w (${lr.leagueName}).")
            }
            add("")
            if (lr.reward > 0) {
                add("Вы заняли ${lr.place}-е место из ${lr.total} и получили в награду ${lr.reward} фантиков.")
            } else {
                add("Вы заняли ${lr.place}-е место из ${lr.total}.")
            }
        } else {
            for (lr in recipient.leagueResults) {
                add("")
                add("${lr.leagueName} (${lr.total} участников):")
                lr.winnerPublicName?.trim()?.takeIf { it.isNotEmpty() }?.let { w ->
                    add("Победитель: $w")
                }
                if (lr.reward > 0) {
                    add("Вы заняли ${lr.place}-е место и получили ${lr.reward} фантиков.")
                } else {
                    add("Вы заняли ${lr.place}-е место.")
                }
            }
            add("")
            add("Итого за серию: +${recipient.totalReward} фантиков.")
        }
        add("")
        add("Теперь у вас ${recipient.balanceAfter} фантиков.")
    }
    return lines.joinToString("\n")
}
```

### 5.9 Деактивация лиги для серии

- `DELETE /admin/series/{id}/leagues/{leagueId}` → `series_league.enabled = false`.
- **Блокируется**, если в этой лиге серии есть хотя бы одна `fantasy_team` (`400 Bad Request`).
- После финализации серии команды зафиксированы — деактивация допустима (но бессмысленна).

### 5.10 Маркетплейс и recycle с учётом лиг

Существующие блокировки расширяются на все лиги:

- **Маркетплейс**: нельзя создать листинг (`MarketplaceService.createListing`), если карта стоит в команде **любой** лиги **любой** нефинализированной серии. Та же проверка, что сейчас — но `FantasyTeamCard` теперь может быть в нескольких `FantasyTeam` (разных лиг).
- **Переработка**: нельзя переработать карту (`CardLifecycleService.recycleCard`), если она в команде любой нефинализированной лиги.
- **Legendary upgrade**: нельзя апгрейдить, если карта в команде любой нефинализированной лиги (§5.2).

Текущий код проверяет `FantasyTeamCardRepository.existsByUserCard_IdAndFantasyTeam_Series_FinalizedFalse` — с лигами этот запрос автоматически покрывает все лиги, т.к. `FantasyTeamCard` привязана к `FantasyTeam`, а не к лиге напрямую.

### 5.11 Скоринг и лиги

Скоринг **не зависит от лиги**: одни и те же игры серии, одна формула `(base + Σachievement) × rarity_modifier`. Разные команды в разных лигах содержат разные карты → разные `FantasyTeam.total_score`. Лидерборд per-league = `WHERE ft.series_league_id = :slId ORDER BY total_score DESC`.

Одна и та же `user_card` в командах двух лиг получит **одинаковый** score (те же игры, тот же игрок), но это не дублирование — каждая `FantasyTeam` независима, просто совпадает результат карты.

## 12. Принятые решения (из обсуждения)

1. **Бюджетная лига по умолчанию**: активируется для **всех** новых серий автоматически. Админ может деактивировать per-series через `series_league.enabled = false`.

2. **Изменение ценности после дедлайна**: **не** пересчитываем валидацию отправленных бюджетных команд. Валидация ценности выполняется только при `POST/PUT` команды. Если админ изменил `economy_config` после дедлайна, уже зафиксированные команды не затрагиваются.

3. **EPIC→LEGENDARY в бюджетной команде**: **блокировать апгрейд**. Если карта стоит в команде **любой** лиги серии с `finalized = false`, апгрейд отклоняется (`400`). Пользователь должен сначала убрать карту из команды.

4. **Одна карта — несколько лиг**: 1 use за каждую лигу. Карта может быть в ≤ `uses_remaining` лигах одной серии (§4.3).

5. **Турнирный лидерборд**: только по основной лиге. Бюджетная лига не участвует в турнирном рейтинге (§8.6).

6. **Главная «Состав на серию»**: показывать per-league статус (✓/✗) на карточке серии (§8.5).

7. **Новая SYSTEM лига**: `series_league` создаётся автоматически только для **новых** серий. Для существующих — не мигрируется (админ может добавить вручную при необходимости).

8. **Деактивация лиги mid-series**: **блокируется**, если в этой лиге серии есть хотя бы одна команда. Админ должен сначала убедиться, что команд нет, или дождаться финализации (§5.9).

## 14. Исследование оптимального бюджетного кэпа

> **Статус:** `achievement_bonus=10`, базы **25/40/80/370**; **принят** кэп **175**. Сетка 100…250; выше 250 не смотрим. `python3 scripts/budget_league_cap_check.py`.

### Контекст

`card_value = base_rarity + achievement_count × 10` (`card.value.achievement_bonus` = **10**). Реф. итоги: **C=25, R=50, E=100, L=400** (§2.2).

| Редкость | База `card.value.*` | Ач. (реф.) | +ач | Итого |
|----------|---------------------|------------|-----|-------|
| COMMON | 25 | 0 | 0 | **25** |
| RARE | 40 | 1 | 10 | **50** |
| EPIC | 80 | 2 | 20 | **100** |
| LEGENDARY | 370 | 3 | 30 | **400** |

Ниже: 3 роли, **value_cap** = **100…250** в колонках (**✓** = Σ ≤ cap). **Принято:** `league.budget.value_cap` = **175**; «радуга» 1C+1R+1E = **175** ровно.

| Кэп | Допустимо | Смысл |

**3×E (300)**, все составы **с L** (min **2C+L = 450**) и **3E** **не** влезают в cap ≤ 250. **Принято:** `value_cap` = **175** → 6/20, «радуга» **1C+1R+1E=175** ровно, **2R+E=200** **не** допускается (нужен cap ≥ 200).

**Сравнение:** 200+ даёт 2R+E и 7/20; 225+ — двойной эпик 1C+2E; 250 — 1R+2E, 9/20.

### 3. Принятое решение (TMA, бюджет)

- `card.value.COMMON` = **25**; `league.budget.value_cap` = **175** (§2.2, §6.1). Допустимых 3-ролевых схем: **6/20**; **легендарки** — только **MAIN** (min L-ростер 450). **2R+E (200)** при 175 **запрещён** — кто хочет такую тройку, **MAIN** или **override** cap в админке (≥ 200).
- Сетка **200 / 225 / 250** — **альтернативы** из §2 выше, если сочтёте 175 **слишком** жёстким.
