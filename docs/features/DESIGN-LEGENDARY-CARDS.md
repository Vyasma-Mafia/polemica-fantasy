# Polemica Fantasy — Легендарные карты (Design Document)

> **Статус:** СОГЛАСОВАН — готов к реализации  
> Общий контекст системы: [`../architecture/DESIGN.md`](../architecture/DESIGN.md) (§10 Phase 4+, легендарный апгрейд).

## 1. Мотивация

Сейчас LEGENDARY карты можно получить **только** от администратора — они запрещены в паках.
Это делает их редкими, но неинтересными: пользователь никак не влияет на их получение.

**Цель:** дать пользователям возможность **апгрейдить** EPIC-карты до LEGENDARY.
Пользователь берёт существующую EPIC-карту, выбирает +1 перк и получает
LEGENDARY-версию того же игрока. Это дешевле, чем создание с нуля, но требует
предварительной «инвестиции» в EPIC-карту.

### Что это даёт
- **Прокачка коллекции:** ощущение «апгрейда» привязывает к карте эмоционально
- **Fantiki-sink:** 400 ₣ за апгрейд + стоимость EPIC-карты (пак/продление)
- **Стратегия:** выбор +1 перки к уже имеющимся двум — осознанное решение
- **Баланс:** лимит 1 LEGENDARY на команду не позволяет доминировать

## 2. Основная механика

### 2.1 Апгрейд EPIC → LEGENDARY

Пользователь в TMA:

1. **Выбирает EPIC-карту** из своей коллекции (с `uses_remaining > 0`, не в команде незавершённой серии)
2. **Выбирает +1 перк** из каталога (кроме тех, что уже есть на карте)
3. **Подтверждает** и оплачивает апгрейд в фантиках
4. EPIC-карта **трансформируется** в LEGENDARY: тот же `UserCard`, но с новым `CardTemplate`

### 2.2 Трансформация карты

Операция **in-place** — `UserCard` остаётся тот же (тот же `id`, тот же владелец):

| Поле UserCard        | До апгрейда (EPIC)                     | После апгрейда (LEGENDARY)                        |
|----------------------|----------------------------------------|---------------------------------------------------|
| `id`                 | Без изменений                          | Без изменений                                     |
| `card_template_id`   | EPIC-шаблон (игрок, 2 перки)         | LEGENDARY-шаблон (тот же игрок, 3 перки)         |
| `uses_remaining`     | N (текущее значение, > 0)              | N + 1                                             |
| `times_renewed`      | Без изменений                          | Без изменений (история продлений сохраняется)     |
| `crafted_by_*`       | NULL                                   | `telegram_user_id` того, кто апгрейдил            |
| `acquired_at`        | Без изменений                          | Без изменений                                     |

**CardTemplate для LEGENDARY:** как и в auto-gen паках — если `CardTemplate` с идентичным
набором (тот же `fantasy_player` + `LEGENDARY` + те же 3 `perk_id`) уже существует —
используется он; иначе создаётся новый.

### 2.3 Выбор перки

- Ровно **+1 перк** к уже имеющимся на EPIC-карте
- Из **полного** каталога `perk`, **кроме** уже присутствующих на карте
- EPIC-карта имеет 2 перки → пользователь выбирает из оставшихся 7
- Бонус за перк — **системный** (`Perk.bonus_points`), без override

### 2.4 Предусловия для апгрейда

| Условие                                     | Иначе                                    |
|----------------------------------------------|------------------------------------------|
| Карта принадлежит пользователю               | 400: «Card not found or not owned»       |
| Карта редкости EPIC                          | 400: «Only EPIC cards can be upgraded»   |
| `uses_remaining > 0`                         | 400: «Renew the card before upgrading»   |
| Карта НЕ в команде незавершённой серии       | 400: «Cannot upgrade a card in an active team» |
| Достаточно фантиков                          | 400: «Insufficient balance»              |
| Выбранное перк не дублирует имеющиеся  | 400: «Perk already on this card»  |

### 2.5 Свойства карты после апгрейда

| Свойство             | Значение                                      |
|----------------------|-----------------------------------------------|
| Редкость             | LEGENDARY                                     |
| Модификатор очков    | ×1.25 (вместо ×1.15 у EPIC)                  |
| Перки           | 3 штуки (2 от EPIC + 1 выбранное)            |
| Использования        | `старые uses_remaining + 1`                   |
| Переработка          | `recycle.value.LEGENDARY` (сейчас 200 ₣)     |
| Продление            | `renewal.cost.LEGENDARY` (сейчас 250 ₣)      |

## 3. Экономика

### 3.1 Стоимость апгрейда

| Параметр               | Значение | economy_config key           |
|------------------------|----------|------------------------------|
| Стоимость апгрейда     | **400**  | `legendary.upgrade.cost`     |

Обоснование: EPIC-карта уже «стоит» пользователю (пак + возможное продление).
400 ₣ — дополнительная инвестиция, но доступнее, чем создание с нуля (было 800).

### 3.2 Полная стоимость владения LEGENDARY

```
Стоимость EPIC (пак ~100-300 ₣)
  + возможные продления EPIC (до 2 × 150 ₣ = 300 ₣)
  + апгрейд (400 ₣)
  + продления LEGENDARY (до 2 × 250 ₣ = 500 ₣)
= от ~500 до ~1500 ₣ за полный жизненный цикл
```

### 3.3 Продление и переработка

Единая стоимость для всех LEGENDARY (crafted и admin-issued):
- Продление: `renewal.cost.LEGENDARY` (сейчас 250 ₣)
- Переработка: `recycle.value.LEGENDARY` (сейчас 200 ₣)
- Макс. продлений: `renewal.max_times` (сейчас 2)

`times_renewed` переносится при апгрейде. Если EPIC-карта была продлена 1 раз,
после апгрейда у LEGENDARY останется 1 продление из макс. 2.

### 3.4 Ограничение в команде

**Макс. 1 LEGENDARY на фэнтези-команду за серию.** Настраивается через `economy_config`.
Распространяется на все LEGENDARY (и upgraded, и admin-issued).

## 4. Лимит LEGENDARY в команде

### 4.1 Правило

При сборке фэнтези-команды (`POST/PUT /series/{id}/fantasy-team`) — максимум **1 карта**
с `rarity = LEGENDARY` на команду.

### 4.2 Где проверяется

- **Backend:** `UserFantasyTeamService.attachCards` — после существующих проверок
  добавляется: `count(rarity == LEGENDARY) ≤ legendary.team.max_per_series`
- **TMA:** `TeamPage` — если в команде уже есть LEGENDARY, остальные LEGENDARY disabled
  с подсказкой «Только 1 легендарная карта на команду»

### 4.3 Ошибка при нарушении

HTTP `400`: `"Maximum 1 LEGENDARY card allowed per fantasy team"`

## 5. Моменты, которые стоит учесть

### 5.1 Конфликт ролей перков

EPIC-карта уже имеет 2 перки с определёнными `applicable_roles`.
При выборе +1 перки пользователь должен видеть, на каких ролях она сработает.
Если 2 из 3 перков — шерифские, карта будет сильна только на шерифе.

Рекомендация: в UI показать applicable roles для каждого варианта.

### 5.2 Источник карты (crafted_by)

На `UserCard` добавляется `crafted_by_telegram_user_id`:
- `NULL` — карта из пака или от админа
- `!= NULL` — карта апгрейднута пользователем

**В UI пока не отображается** — поле на будущее (аналитика, возможная метка «Апгрейд»).

### 5.3 Карта в команде после апгрейда

Апгрейд **блокируется**, если карта в команде незавершённой серии (аналог recycle).
Причина: смена `card_template_id` на карте, которая уже участвует в скоринге,
может привести к несогласованности данных.

### 5.4 EPIC-карты с 0 использований

Нельзя апгрейдить истёкшую карту. Пользователь должен сначала продлить (renew)
EPIC-карту, а затем апгрейдить. Это дополнительный fantiki-sink.

### 5.5 Откат апгрейда

Апгрейд **необратим**. Нельзя «даунгрейднуть» LEGENDARY обратно в EPIC.
Но можно переработать (recycle) за `recycle.value.LEGENDARY`.

### 5.6 Красивый дизайн и анимация (отдельная задача)

LEGENDARY-дизайн и анимация апгрейда — отдельная задача.
Backend предоставляет данные: `rarity = LEGENDARY`, 3 перки, `craftedBy`.

### 5.7 Взаимодействие с существующими механиками

| Механика                | Поведение                                     |
|-------------------------|-----------------------------------------------|
| Сборка команды          | Макс. 1 LEGENDARY на команду; проверка uses, серии, уникальность игрока |
| Скоринг                 | `(base + Σperks) × 1.25` (3 перки вместо 2) |
| Финализация серии       | Декремент `uses_remaining` как обычно          |
| Переработка (recycle)   | Доступна, `recycle.value.LEGENDARY` (200 ₣)   |
| Продление (renew)       | Доступно, `renewal.cost.LEGENDARY` (250 ₣)    |
| Лимит продлений         | `renewal.max_times` (2), `times_renewed` переносится |
| Выдача из пака          | LEGENDARY запрещён в паках — без изменений     |
| Выдача от админа        | Остаётся, `crafted_by = null`                  |

## 6. Модель данных

### 6.1 Новые поля

**`user_card` — новый nullable столбец:**
```sql
ALTER TABLE user_card
    ADD COLUMN crafted_by_telegram_user_id BIGINT
        REFERENCES telegram_user(id);
```

### 6.2 Новые ключи `economy_config`

```sql
INSERT INTO economy_config (key, value, description) VALUES
    ('legendary.upgrade.cost', '400', 'Стоимость апгрейда EPIC → LEGENDARY (фантики)'),
    ('legendary.team.max_per_series', '1', 'Макс. LEGENDARY карт в фэнтези-команде на серию');
```

### 6.3 Flyway миграция

Одна миграция `V19__legendary_upgrade.sql`:
- ALTER TABLE `user_card` + FK
- INSERT `economy_config` ключи

### 6.4 Без изменений в CardTemplate / Perk

Существующая модель полностью подходит. `CardTemplate` с `LEGENDARY` + 3 перки
создаётся или переиспользуется (как в auto-gen паках).

## 7. API

### 7.1 User API (TMA)

| Method | Path                              | Description                                   |
|--------|-----------------------------------|-----------------------------------------------|
| GET    | `/legendary-upgrade/info`         | Стоимость апгрейда, баланс                    |
| POST   | `/legendary-upgrade`              | Апгрейдить EPIC-карту до LEGENDARY            |
| GET    | `/perks`                   | Каталог перков (уже существует)           |

**`GET /legendary-upgrade/info`** Response:
```json
{
  "cost": 400,
  "userBalance": 1200,
  "canAfford": true
}
```

**`POST /legendary-upgrade`** Request:
```json
{
  "userCardId": 123,
  "perkId": "SURVIVED_TILL_END"
}
```

Response (success): `UserCardItemDto` (обновлённая карта — теперь LEGENDARY с 3 перками).

Ошибки:
- `400` — карта не найдена или не принадлежит пользователю
- `400` — карта не EPIC
- `400` — `uses_remaining = 0` (сначала renew)
- `400` — карта в команде незавершённой серии
- `400` — недостаточно фантиков
- `400` — перк уже есть на карте
- `400` — неизвестный `perkId`

### 7.2 Admin API

Дополнительные admin-эндпоинты не требуются. Новые ключи `economy_config`
доступны через существующий CRUD.

### 7.3 Изменение в существующем API

**`POST/PUT /series/{id}/fantasy-team`** — добавляется валидация:
LEGENDARY карт в команде ≤ `legendary.team.max_per_series`.

## 8. Backend (сервисный слой)

### 8.1 Новый сервис: `LegendaryUpgradeService`

```kotlin
@Service
class LegendaryUpgradeService(
    private val userCardRepository: UserCardRepository,
    private val fantasyTeamCardRepository: FantasyTeamCardRepository,
    private val cardTemplateRepository: CardTemplateRepository,
    private val cardTemplatePerkRepository: CardTemplatePerkRepository,
    private val perkRepository: PerkRepository,
    private val economyConfigService: EconomyConfigService,
    private val userService: UserService,
) {
    @Transactional
    fun upgradeToLegendary(user: TelegramUser, request: UpgradeLegendaryRequest): UserCard {
        // 1. Найти UserCard, проверить ownership
        // 2. Проверить rarity == EPIC
        // 3. Проверить uses_remaining > 0
        // 4. Проверить: не в команде незавершённой серии
        // 5. Валидировать perkId (exists, not already on card)
        // 6. Проверить баланс
        // 7. Найти или создать LEGENDARY CardTemplate (тот же игрок, 2 старых + 1 новая перк)
        // 8. Списать фантики (reason = LEGENDARY_UPGRADE)
        // 9. Обновить UserCard: card_template_id, uses_remaining += 1, crafted_by
        // 10. Вернуть обновлённую карту
    }
}
```

### 8.2 Изменение в `UserFantasyTeamService.attachCards`

```kotlin
val legendaryCount = cards.count { it.cardTemplate!!.rarity == Rarity.LEGENDARY }
val maxLegendary = economyConfigService.getLegendaryTeamMaxPerSeries()
if (legendaryCount > maxLegendary) {

}
```

## 9. Frontend (TMA)

### 9.1 Точки входа (два входа — один флоу)

| Откуда | Что видит пользователь |
|--------|----------------------|
| **Магазин** → «Улучшить до легендарной» | Шаг 1 → Шаг 2 → Подтверждение |
| **Коллекция** → модалка EPIC → «Улучшить» | Шаг 2 → Подтверждение (карта уже выбрана) |

**Магазин** — основная точка входа. Рядом с паками — секция/кнопка «Улучшить до легендарной».
Это место, где пользователь тратит фантики.

**Коллекция** — шорткат. На модалке деталей EPIC-карты (с `uses_remaining > 0`,
не в команде незавершённой серии) — кнопка «Улучшить до LEGENDARY».
Аналогично тому, как Recycle и Renew уже доступны из модалки карты.

### 9.2 UX-флоу

1. **Шаг 1 — Выбор EPIC-карты** (пропускается при входе из коллекции):
   сетка EPIC-карт пользователя; подходящие (uses > 0, не в команде) активны,
   остальные — disabled с подсказкой причины
2. **Шаг 2 — Выбор +1 перки:** список доступных перков (без уже имеющихся на карте);
   для каждой — название, описание, applicable roles
3. **Подтверждение:** превью:
   - «Было: EPIC, 2 перки, ×1.15, uses: 3»
   - «Станет: LEGENDARY, 3 перки, ×1.25, uses: 4»
   - «Стоимость: 400 ₣»
   - Кнопка «Улучшить за 400 ₣»
4. **Результат:** анимация (отдельная задача) + обновлённая карта в коллекции

### 9.3 Изменение в TeamPage

Если в команде уже есть LEGENDARY, остальные LEGENDARY disabled
с подсказкой «Только 1 легендарная карта на команду».

### 9.4 Изменение в Help-странице

Добавить секцию «Легендарные карты» с описанием апгрейда и ограничения в команде.

### 9.5 Админка

Новые ключи `economy_config` автоматически появятся на странице `/economy`.

## 11. Принятые решения

| Вопрос | Решение |
|--------|---------|
| Механика создания | Апгрейд существующей EPIC → LEGENDARY (не создание с нуля) |
| Что происходит с картой | Трансформация in-place: тот же `UserCard`, новый `CardTemplate` |
| Игрок | Остаётся тот же (от EPIC-карты) |
| Перки | 2 от EPIC + 1 выбранное пользователем = 3 |
| Стоимость | 400 ₣ (настраиваемо через `economy_config`) |
| `uses_remaining` | Переносится + 1 (было 3 → станет 4) |
| `times_renewed` | Переносится без изменений |
| Карта с 0 uses | Нельзя — сначала renew |
| Карта в команде | Нельзя — блокировка как при recycle |
| Лимит в команде | Макс. 1 LEGENDARY на команду за серию |
| Лимит на создание | Нет — цена единственный барьер |
| Бонусы перков | Системные (без override) |
| Поле `crafted_by` | Добавить, пока не отображать в UI |
| Продление/переработка | Единая стоимость для всех LEGENDARY |
| Анимация | Отдельная задача (дизайн) |
| Откат апгрейда | Необратим |

## 12. Пример user journey

> У Алекса есть EPIC-карта «МихалычЪ» с перками WON_GAME и BEST_MOVE.
> Карта имеет 3 uses_remaining. Баланс: 900 ₣.
>
> 1. Открывает коллекцию → нажимает на EPIC-карту «МихалычЪ»
> 2. Видит кнопку «Апгрейд до LEGENDARY»
> 3. Выбирает +1 перк: SURVIVED_TILL_END (все роли)
> 4. Видит превью:
>    - Было: EPIC ×1.15, 2 перки, 3 uses
>    - Станет: LEGENDARY ×1.25, 3 перки, 4 uses
>    - Стоимость: 400 ₣
> 5. Подтверждает → анимация → карта обновлена в коллекции
> 6. Баланс: 500 ₣. Карта «МихалычЪ» теперь LEGENDARY.
>
> При сборке команды Алекс ставит LEGENDARY-карту в слот 1,
> EPIC и RARE — в слоты 2 и 3 (вторую LEGENDARY поставить нельзя).
>
> Каждая игра серии: `(base + до 3 бонусов) × 1.25` вместо `(base + до 2 бонусов) × 1.15`.
